# 0020. Reporting queries, and the shape of the dashboard they feed

- Status: Accepted
- Date: 2026-10-01

## Context
The dashboard asks for a handful of numbers, a time series, and a ranked list for each of a dozen dimensions.
Two things constrain how: which table can honestly answer a question, and the site's own timezone.

[ADR 0007](0007-events-sessions-and-additive-rollups.md) split the data on additivity. Pageviews may be summed, so
they live in an hourly rollup. Unique visitors may not — the same person seen in two hours is one visitor — so
they are counted from sessions. That split decides the source of every number here rather than being a preference.

## Decision
- **One parameterized breakdown endpoint**, `/stats/breakdown?dimension=…`, instead of one endpoint per report.
  The column each dimension groups by is chosen from an enum in the code, never from the request, so nothing a
  caller sends can shape the SQL.
- **Most dimensions are session attributes** (source, country, region, city, browser, operating system, device,
  entry and exit page, UTM), so one pass over `api_sessions` answers visitors, visits and pageviews together.
  **Pages are not**: a visit covers many pages, so that breakdown is grouped from `api_events`, which is also the
  only place a per-page visitor count can come from.
- **Dates are the site's, not the viewer's.** `from` and `to` are local days resolved with the timezone Site
  Management holds, so two people in different places looking at one site see the same numbers. Day buckets are
  cut with `at time zone` in SQL; hour buckets need no zone, since an hour is an hour everywhere.
- **Empty buckets are returned with zeroes**, generated by the query rather than left out, because a chart has to
  draw the quiet days instead of closing the gap.
- **A value that is not known is its own row**, under an empty key the dashboard prints as "Unknown", so a
  breakdown still adds up to the total.
- **The dashboard draws one measure at a time.** Visitors and pageviews are different scales; two y-axes would let
  the scaling decide what the picture says. A toggle switches which one is drawn, which also means a single
  series — no legend, and no second colour to find in a theme that is deliberately without hue. The palette was
  checked rather than eyeballed: as a categorical palette the neutral ramp fails (no chroma, adjacent steps
  indistinguishable), while as a single series or a sequential ramp it is sound. The form follows that result.
- Every row of a ranked list carries its own number, so the bar beside it is a comparison aid rather than the only
  way to read the value.

## Consequences
- The top pages report reads `events`, which is the heaviest query the dashboard makes and the one that will not
  benefit from the rollup. Ranking pages by pageviews alone would have been cheap; showing visitors per page is
  worth more to the reader. Whether it stays that way is a question for the load tests, not for taste.
- A rollup is hourly, so in a zone whose offset is not a whole number of hours — `Asia/Kolkata` at +05:30, for
  instance — a local day boundary falls inside an hour, and the pageview series rounds it to the nearest one.
  Everything taken from sessions, which is to say visitors, visits, bounce rate and duration, stays exact in every
  zone. Whole-hour zones, which is most of them, are exact throughout.
- The time series is drawn in the browser, so the same numbers are also rendered server side as a table. Without
  it a reader using assistive technology, or anyone whose JavaScript did not run, would be left with an empty box.
- A country is sent as its ISO code and named in the browser, which already knows every country in the reader's
  own language. A region and a city are sent with the name ingest resolved, because nothing in the browser can
  name those.
